# 聊天代理的开发经验：从上下文、投递到隐私发布

这份文档记录本修改版开发中可复用的工程经验。案例已抽象化，不包含真实聊天、账号、个人经历、参考录音或音色资产。它不是对模型自然度的完成声明，也不是一套通用的“拟人提示词”。

## 1. 先找到错误发生在哪一层

一条 QQ 回复会经过多层处理，用户看到的现象不能直接证明某一层有问题。

| 层 | 应核对的证据 | 常见误判 |
| --- | --- | --- |
| 网关接收 | 原消息 ID、来源、原时间和消息段 | 显示 connected 就认为没有漏消息 |
| 会话输入 | 实际会话、预设、当前输入与派生上下文 | 会话标题正确就认为系统提示正确 |
| 模型输出 | 最终正文、工具调用、结束状态 | 把普通正文里的工具标签当成工具执行 |
| 出站处理 | 清洗、气泡拆分、钩子和目标 | 模型正文正确就认为对方收到的也正确 |
| 制作与发送 | 合成/转换耗时、排队、提交与回执 | 把总延迟都算给模型或 QQ |
| 持久化 | 成品、账本、真实回执与补记 | 有文件或“答应了”就记成已经送达 |

排查时沿一条消息逐层比对，不从最后一句反推整条链路。表情、引用和语音在不同日志中的表示可能不同，应先区分格式差异和实质改写。

相关实现：`src/chat/hub.js`、`src/onebot/client.js`、`src/chat/outbound.js`。

## 2. “说话像 AI”常常包含上下文问题

只追加“自然一点、简短一点”容易得到更短的套话。更有用的检查顺序是：

1. 当前输入新增了什么事实、意愿或更正。
2. 代理上一轮已经说过什么，实际发出了什么。
3. 自动召回是否带来了不相关的旧情绪、旧任务或旧拒绝。
4. 角色设定有没有被扩写成不存在的共同生活经历。
5. 规则是否暗示固定的安慰、劝和、催睡或结束流程。

关心不必每轮附带存在保证、相处策略或建议。对方确实询问在不在时仍应正常回答；目标是减少机械套用，不是禁止正常亲近。

### 二次改写器的教训

发送前再调用一个模型，可能同时增加延迟和语义漂移。如果它缺少完整身份、原话、工具结果和上下文，甚至会把原本正确的回答改错。

本修改版取消正常聊天发送路径上的在线二次改写，优先修正主模型拿到的资料与约束。离线核对工具可以保留，但不能因为文件存在就认为它仍在每轮发送时运行。

### 不靠固定答案伪装自然

- 不建立“所有安慰词一律删除”的全局禁词表。
- 不把直白、有个性或短暂犹豫统一改成客服式温柔。
- 不为口语化强行填语气词、凑句数或机械删标点。
- 不把有限回放通过解释成未来所有聊天都会自然。

相关实现：`src/persona/personas.js`、`src/chat/conversation-replay.js`。`src/chat/conversation-quality.js` 是离线诊断用途。

## 3. 记忆需要来源、时间和完成状态

记忆不只是一个“相似文本列表”。至少要分清：

| 记录 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 人类原话 | 这个人在当时这样说过 | 第三人的动机一定如此 |
| 自动提炼 | 对原话的有来源概括 | 概括永远准确、现状永远不变 |
| 代理旧回复 | 当时说过这句话 | 其中猜测或虚构经历真实发生过 |
| 代理承诺 | 曾经答应做某事 | 已经执行或完成 |
| 工具结果 | 某项实际操作的结果 | 对方已经看到、满意或理解 |
| 日记正文 | 写过、分享过这段文字 | 文中所有主观推断都是真实事实 |

### 一次性嘱咐不能自动变成永久任务

“有空提醒一下”“等某件事结束后再问”有具体情境。不能仅因为出现“你的任务”就保存为长期职责。抽取提示、写入校验、上下文展示和检索标签必须使用一致的判断。

本修改版保留较早任务供明确查询，不把它们每轮都塞进常驻上下文。减少自动暴露不等于删除，也不能擅自标为完成或取消。明确盘点任务时仍须能够查全。

常驻展示、自动联想和显式工具检索应分开：

- **常驻**：少量稳定身份和明确表达偏好。
- **自动联想**：与当前具体话题相关，标注当时来源和时间。
- **显式查询**：允许查完整历史，保留完成状态与来源边界。

相关实现：`src/features/memory.js`、`src/features/family-memory.js`、`src/features/memory-store.js`。

## 4. 当前状态应从真实账本派生

“今天零篇日记”与“从来没写过日记”是两回事。午夜过后，如果上下文只提供当天计数，模型可能又说成第一篇、忘写了或明天补交。

展示当前状态时，应同时提供最近一次成功记录和当天情况。失败、未确认或预览不能充当成功记录；已取消授权的目标也不能混入当前范围。

同样的原则适用于绘画、翻唱、提醒和文件发送：优先使用实际状态，而不是反复召回过去的计划。

相关实现：`src/modules/diary/family.js`、`src/features/artwork-memory.js`。

## 5. 异常输出和被打断的回复要分情况恢复

### 正文里写出工具名，不代表执行了工具

不要执行任意 XML 或把正文参数猜成工具调用。工具必须走真实调用通道。没有真实开始或结果时，不能对用户声称“正在做”“做好了”。

### 空正文不等于正常沉默

需要区分：明确沉默、后台任务、取消、尚未完成，以及真人追问得到异常空正文。对最后一种情况，可以在原会话中有界恢复；已尝试的副作用工具应复用结果或说明未确认，不能为补一句话重复执行。

### 续答只携带真实已发送内容

新输入打断回复后，未发送草稿不能当作对方已经听到的内容回注。续答也不应重新发送已经成功发出的开头。保留原消息顺序与实际送达记录，比追加一段“不要重复”更可靠。

相关实现：`src/chat/completion-recovery.js`、`src/chat/recovery-context.js`、`src/chat/local-history.js`。

## 6. 重载恢复的关键是“提交边界”

普通语音的状态可按以下顺序理解：

```text
queued → synthesizing → ready → submitting → sent
                                  ↘ uncertain
```

- `ready`：成品已经保存，尚未提交；重新核对权限后可以接续。
- `submitting`：已经跨过提交边界；中断后不能假装一定没发出。
- `sent`：取得有效回执，立即持久化，即使旧实例已经被卸载。
- `uncertain`：无法确认送达；不自动重发，也不记成成功。

进程内锁解决同机重载时的并发制作，持久账本解决重启后的状态恢复。二者不能互相替代。新实例可以只补记迟到的成功回执，不必再次发送。

翻唱与普通 TTS 的成本、成品和恢复策略不同，应各自记账。模型版本、音高和混音参数需要进入缓存标识，避免新音色复用旧成品。

相关实现：`src/voice/outbox.js`、`src/song/studio.js`。

## 7. 语音权限必须按目标执行

“是谁提出请求”与“发往哪里”是两个问题。主人在普通群里请求语音，不代表可以把语音发到普通群。

本仓库将语音输出固定限制为主人/共同主人私聊和指定家庭群，检查点包括：

1. 合成或制作前，避免先花资源再拒绝。
2. 最终消息段生成后，防止钩子重新插入音频。
3. 真正提交网关前，重新读取当前权限。
4. 语音账本恢复和翻唱补发前，重新检查目标。
5. 原始 QQ 动作、嵌套转发与音频文件出口，避免走旁路。

普通聊天中的语音文本可以降为文字。已有音频文件不能凭空“降为文字”；范围外应停止发送。无法核对内容的转发引用也不能假装已经确认不含语音。

测试应覆盖正常允许、普通白名单仍被拒绝、主人在普通群请求、制作途中撤权、重载恢复、强制发送和原始接口。只验证工具是否可见不够。

相关实现：`src/voice/access.js`、`src/chat/hub.js`、`src/onebot/client.js`；回归见 `test/private-voice-scope.test.js`。

## 8. 用真实路径验证，明确验证的边界

建议把验证分为几类，报告时分别说明：

| 验证 | 适合回答的问题 | 仍不能证明 |
| --- | --- | --- |
| 纯函数测试 | 权限、解析、状态迁移是否符合约定 | 真实模型和网关是否正常 |
| 假宿主 + 假网关 | 插件调用、打断、回执、重载是否接通 | 真实 QQ 客户端收到了什么 |
| 隔离真实模型回放 | 当前提示与上下文下会怎样回答 | 后续所有场景都自然 |
| 真实制作 + 拦截发送 | TTS/分离/换声/混音和发送准备是否接通 | 实际 QQ 端到端时延 |
| 正常生产观察 | 真实请求的实际表现 | 所有历史故障的根因 |

保留失败回放，再加入换一种说法和多轮延续。不要只保存满意的样例，也不要只数“改写成功几次”就宣称语义准确。

延迟至少分开测：模型生成、制作、排队、提交和回执。音频有效、音高接近、主观音色相似和用户满意也是不同结论。

## 9. Windows 上的几个实际问题

- 先确认 PowerShell 版本，不假定所有编码参数都可用。
- shell 引号与 JSON 编码不是一回事，尤其注意 `$()`、反引号和多行正文。
- 隐藏启动后台程序；终止任务时核对自己拥有的进程及其子进程，不能按宽泛名称杀进程。
- Python 虚拟环境可能有启动器和实际解释器两层，超时取消要处理完整的已拥有进程树。
- 缓存目录和共享环境可能影响模型初始化；隔离新依赖与实验缓存，保留可回滚的生产环境。
- 报告应使用确认过的实际结果，不把命令启动、文件存在或网页打开当作验收完成。

## 10. 开源发布应从干净快照开始

工作目录通常混有运行数据、研究脚本、输出和私人回归夹具。只写 `.gitignore` 不能清除已经提交过的历史。

本次发布采用：

1. 按目录和文件类型白名单构建独立源码快照。
2. 排除账号配置、Cookie、密钥、聊天、记忆、日志、缓存、备份和个人媒体。
3. 排除个人音色 ID、参考录音、数据集、说话人资产和训练权重；保留通用接口代码。
4. 将公开测试中的身份改为合成数据，移除基于私人聊天的回归夹具。
5. 保留上游许可和署名；确认所带默认素材来自上游公开版本。
6. 在干净快照上运行测试，扫描当前文件和可达提交历史。
7. 上传后核对远端提交、文件树和匿名访问，分别记录本地测试与 GitHub 测试结果。

密钥扫描对公开协议常量和假测试键可能误报。应核实来源、把占位值写得明确，必要时做精确说明；不要用忽略整个测试目录或关闭扫描来掩盖问题。零发现仍不等于能识别所有可能的秘密格式。

## 11. 改进时保留哪些判断原则

- 先修数据来源和状态，再考虑增加模型步骤。
- 身份、事实、计划、执行和送达分开记录。
- 重载后接续明确未提交的工作，对未知送达保持诚实。
- 权限在真正产生副作用前复查，不能只靠提示词。
- 日常对话允许灵活表达，工具权限和隐私出口需要硬约束。
- 有针对性地验证具体风险；充分验证后交付，不无限追加同义测试。
- 用户收窄范围时收窄；追加授权后再扩展。保留未完成项和失败证据，不把阶段结果写成全部完成。

本仓库仍有生成式模型的事实推断、措辞和多轮自然度边界。欢迎提交合成的最小复现、明确的预期和验证结果；请不要在公开 issue 中粘贴私人聊天、账号凭据或声音样本。
